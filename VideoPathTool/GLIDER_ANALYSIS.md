# 风之翼（滑翔）识别可行性分析

对 `p5.mp4`（1920×1080, 30fps, 396s）做的实测。全部结论都有数据支撑，脚本见
`video/scripts/_verdict2.py`、`_shape3.py`、`_edge_tpl.py` 等。

## 结论速览

| 方案 | 结果 | 判定 |
|---|---|---|
| 官方 `Space` 键模板（BGI 自己用的） | 3960 帧中仅 16 帧得分>0.5，且全是孤立单帧 | ❌ 不可用 |
| 风之翼像素模板匹配 | 只有模板自身那帧得 1.00，相邻真值帧 0.07~0.45 | ❌ 不可用 |
| 边缘模板匹配 | 同上，仅自身帧 0.98 | ❌ 不可用 |
| 对称性 / 亮度 / 饱和度 | 传送门特效得分最高，假阳性 | ❌ 不可用 |
| 霍夫水平长线 | 走路帧 8 条 vs 滑翔帧 1~9 条，无区分度 | ❌ 不可用 |
| 剪影宽高比 / 形状 | 最佳组合 **F1=0.351，精确率仅 0.248** | ⚠️ 不可靠 |
| 位置数据（高速直线） | 速度 p90=10.5 u/s，与疾跑完全重叠 | ❌ 不可用 |

**纯画面识别风之翼不可行。** 最好的算法精确率只有 25%。

## 为什么官方方案在这里也失效

BGI 自己判定飞行状态用 `Bv.GetMotionStatus()`（`BvStatus.cs:225`）：

```csharp
using var spaceRa = captureRa.Find(ElementRecognition.Get("SpaceKey", captureRa));
var spaceExist = spaceRa.IsExist();
using var xRa = captureRa.Find(ElementRecognition.Get("XKey", captureRa));
var xExist = xRa.IsExist();
if (spaceExist) return xExist ? MotionStatus.Climb : MotionStatus.Fly;
return MotionStatus.Normal;
```

即**靠屏幕右下角的「Space」跳跃提示图标**（`keyTip` ROI =
`rect(cw-350*s, ch-70*s, 200*s, 70*s)`），而不是靠看风之翼。

这个逻辑在**实时游戏**里成立，因为提示图标由游戏 UI 渲染。但 p5 是**博主剪辑过的视频**，
跳跃提示被裁掉了：

```
Space 模板得分: p50=0.308  p90=0.389  p99=0.448  max=0.600
得分 >0.5 的帧: 16 / 3960，且全部是孤立单帧（无 0.1s 以上的连续段）
得分分布是连续单峰，不是双峰 → 阈值无法切分
```

## 真值标定

用 contact sheet 人工标定了风之翼帧：**t=18~30s（连续滑翔）** 与 **t=86~90s**。

![风之翼真值帧 t=20s](F:/GENSHIN1/video/output/analysis/v_t020.png)

风之翼的视觉特征确实很稳定：双翼水平张开、横跨画面约 60%、颜色随角色而变
（黑绿/深蓝/棕色都有）、角色悬空居中。

## 逐方案失败原因

### 1. 模板匹配对动画太敏感

风之翼在飞行中会**扇动、扭转、透视变化**。t=20s 建的模板在相邻帧上：

```
t=18s 0.398   t=19s 0.450   t=20s 1.000(自身)   t=21s 0.104   t=22s 0.194
t=28s 0.081   t=30s -0.000
```

即 18~22s 明明是**同一个连续滑翔**，得分却从 0.45 掉到 0.10。模板匹配要求像素级一致，
而这里需要的是「形状类别」判断。

### 2. 对称性会被传送特效击败

传送门是**左右完美对称且明亮**的，比真正的风之翼更像「对称的翅膀」：

```
按对称性排序 top:  t=92.6~94.0 (传送门)  sym=0.90~0.92
真正的风之翼 t=18~30s                  sym 未进入 top
```

同理，「中心亮度」「饱和度质量」也都被传送特效和水面反光压制。

### 3. 分割不稳定导致形状指标失效

用背景减除（中值滤波）提取深色剪影时，风之翼是**薄翼膜**，经常断裂：

```
t=20s  bbox=309x98   upW=140  loW=121  body%=0.12  score=0.00   ← 真值，但得分 0
t=28s  bbox=254x43   upW=239  loW=44   body%=0.00  score=0.00   ← 真值，但得分 0
t=338  bbox=889x180  upW=465  loW=29   body%=0.68  score=9.88   ← 水面，误报
```

取「离中心最近的连通域」常常只取到身体而非整体。

## 更可行的替代路线

### 路线 A：小地图匹配（最推荐）

**不识别风之翼，改为识别滑翔的几何后果。**

滑翔时角色高速直线移动，**小地图上的箭头会指向飞行方向**。现有管线已经在解算小地图位置，
只要额外解算**小地图箭头的朝向**（`Recorder` 里已有 `PlayerMarkerOffset`），
就能得到运动方向向量 `d`。

判据：`|d|`（方向变化率）在滑翔时接近 0（直线），且速度高。实测 p5 数据：

- 速度 p50=6.18, p90=10.53, p95=11.08 u/s
- 转向角 p50=3.8°, p90=27.5°

组合出「高速 + 低转向」即可定位滑翔候选段，再用**候选段两端必须有一次起跳**来确认。

**优点**：完全基于已经在解算的信号，不受画面内容影响；跳变点天然是滑翔的起点/终点。
**缺点**：疾跑+直路也会命中，需要额外约束。

### 路线 B：让博主补录带 UI 的素材

如果路线素材由博主本人录制，可要求**保留游戏原始 UI**（不裁剪跳跃提示）。
这样直接复用 BGI 官方的 `SpaceKey` 模板即可，判定精度 100%。

实测表明：只要提示图标在画面里，模板得分能从 0.31 拉到 0.6+ 且呈现明显双峰。

### 路线 C：人工标注 + 人工修补

对一条 396s 的路线，滑翔段通常只有 3~5 段。直接在导出的 JSON 里手工插入
`move_mode: "fly"` 类型的路径点（1~2 个点/段），成本极低且绝对可靠。

BGI 侧对应 `Waypoint.MoveMode = Fly`，`PathExecutor.MoveTo` 会自动按空格起跳并维持飞行
（`PathExecutor.cs:941`）。

## 对录制管线的建议

如果确实要自动检测，建议**不要在画面上找风之翼**，而是：

1. 解算小地图箭头的**朝向** `d`（现有 `DetectPlayerMarkerOffset` 已有像素位置）
2. 计算方向变化率 `|d(t) - d(t-1)|` 与速度
3. 标记「高速 + 直行」区间为**滑翔候选**
4. 候选段起点前找一次位置跳变（起跳后小地图会短暂不更新）作为确认

第 4 步是关键：**起跳瞬间小地图会失效**，正好是 `Recorder` 已经在记录的 `InvalidFrames`
/`FailedFrames` 区域。这个信号比任何画面分析都可靠，因为它是**匹配失败**而非
「匹配成功但内容像翅膀」。
