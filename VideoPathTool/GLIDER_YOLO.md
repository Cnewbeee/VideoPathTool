# YOLO 风之翼检测：可行性实测报告

**结论：可行，且明显优于小地图启发式。** 已用实测数据验证并集成进工具。

---

## 1. 为什么值得做

小地图启发式方案（[GLIDER_ROUTEA.md](GLIDER_ROUTEA.md)）在 p5.mp4 上只有 **F1 0.75、精确率 0.64**。
根本原因是游戏把三种东西画成同一种青色：

| 东西 | 何时出现 | 误报后果 |
|---|---|---|
| **风之翼标记** | 展开风之翼时 | — |
| **飞行轨迹线** | 滑翔后留在小地图上 | 长宽比 19~34，比翼还"像翼" |
| **角色披风** | **常驻**，跑动时就会张开 | 形状与翼几乎一样 |

最后一条最致命：披风是角色模型的一部分，跑动时就会展开成翼形。
**人工核查时我曾把 p5 的 108~121s 整段误判为滑翔**（那其实是披风），
这直接说明单靠形状统计无法区分。

学习模型能分开它们，因为差别在**翼展开的形状特征**，而不是某一个可测统计量。

---

## 2. 实测结果

### 数据集（v6，最终模型）

采用**伪标签 + 每窗取最置信帧**的方式构建：用已验证的模型在已确认窗口内逐帧打分，
**只取分数最高的若干帧**，模型没检出的帧直接跳过（既不标正也不标负），彻底避免标签噪声。

| 项 | 数量 |
|---|---|
| 正样本（伪标签） | 141（117 高置信 + 24 新变体） |
| 负样本 | 946（其中 **29 个因落在滑翔窗口内被安全网拦下**） |
| 难负样本窗口 | p5 108~121.5s（披风）、204~214s、218.5~235.5s、240.6~316s、p3 6.8~7.6s、323.5~331.5s 等 |
| 视频 | p5.mp4 (396s) + p3.mp4 (812s) |
| 模型 | yolov8n（3.1M 参数，12.3 MB ONNX） |

### 各代模型对比

| 代 | 训练集 | val mAP50 | val mAP50-95 | 全视频段级检出 | 误报 |
|---|---|---|---|---|---|
| v3 | 194 正 | 0.686 | 0.307 | 14/14（当时真值） | 0 |
| v4 | 126 正 | 0.696 | 0.371 | 19/23 | 1 |
| v5 | 141 正 | 0.683 | 0.379 | 21/29 | 2 |
| **v6** | 141 正 | **0.870** | **0.546** | **26/29** | **1** |
| v7 | 164 正 | 0.749 | 0.481 | 26/29 | 5 |
| v8 | 114 正 / 691 负 | 0.719 | 0.391 | 30/29 | 1 |
| **v9** | 113 正 / 691 负（train 人工修正） | — | — | **26/29** | **0** |
| v10 | 113 正 / 691 负，val 也修正 | **0.940** | **0.716** | 23/29 | 0 |

v10 的 val mAP 是这一列里**唯一可信**的一个（见下），但它没能在真值视频上超过 v9，
所以仍部署 v9。

**v9 是最终模型**（已部署为 `glider.onnx`）。

v9 的意义不在指标数字，而在数据：训练集的框被**逐张人工修正**过 ——
旧标签把角色上半身一起框进去，新标签只框展开的风之翼（117 个正样本全部重画）。
修正后召回从 0.539 提到 0.745，误报降到 0。

**v9 的 val mAP 没有意义**，所以表里留空：训练时验证集的框还是旧风格（259 张一张没改），
预测出来的贴合翼展框和它对不上 IoU，mAP50 只有 0.012 —— 但同一模型在验证集
44 张正样本上能出框 34 张。**标签风格不一致时，val mAP 不能当指标用**，
只能看真值段级评估。同理，`best.pt` 也是按这个失效的 mAP 选的，所以 v9 部署的是
训练末轮的 `last.pt`。

v10 把验证集也修正后重训，val mAP50 直接回到 **0.940**（第 6 轮就有 0.401，
而 v9 到第 40 轮还只有 0.012）——这本身就是"标签风格不一致会毁掉验证指标"的最好证据。

但 v10 在真值视频上没有超过 v9（F1 0.726 / 0.747 对 0.759）。原因是**训练集完全相同**，
两者只差在"用哪个 epoch 出模"：v10 现在能靠可信的 val mAP 选出 `best.pt`，
v9 只能取末轮。差异落在噪声范围内，所以保留 v9。

结论：**这一代的瓶颈不在训练设置，而在数据。** 下次想再提，得补新视频里
没见过的场景（滑翔以外的翼展形态、不同分辨率），而不是继续加轮数。

v7 虽然召回更高（帧级 F1 0.752），但引入了 **5 个真误报** —— 原因是它新增的
22 个窗口里混进了起跳/收翼帧，模型学会了把**奔跑时的披风**当成翼。
这说明迭代不是单调变好的，必须用真值严格评估后再决定采用哪一代。

### 各代的实际检测（3fps 全视频扫描，真值 29 段）

| 代 | p5 | p3 | 合计帧级 | 误报 |
|---|---|---|---|---|
| v6 | 9/7 段，0 误报 | 17/22 段 | P=0.851 R=0.539 F1=0.660 | 1（p3 705.67s 传送道具） |
| v8 | 9/7 段，0 误报 | 16/22 段 | P=0.807 R=0.644 F1=0.716 | 1 |
| **v9** | **9/7 段，0 误报** | **14/22 段** | **P=0.773 R=0.745 F1=0.759** | **0** |
| v10 best | 9/7 段，0 误报 | 14/22 段 | P=0.697 R=0.758 F1=0.726 | 0 |
| v10 last | 9/7 段，0 误报 | 14/22 段 | P=0.752 R=0.742 F1=0.747 | 0 |

v9 的 p3 段级命中反而少三个（14 vs 17），但帧级召回高出近 20 个百分点 ——
它漏掉的是极短的段（零点几秒），却把长段检得更完整。对生成 `fly` 路点来说，
后者更有用：短段本来就会被合并或忽略。

### 关于"再训练一下"

真正的改进来自标注，不是超参 —— v8 把轮数翻倍（100 轮）只是把
F1 从 0.660 拉到 0.716；v9 换成人手修正过的框，同样 120 轮就到了 0.759，
而且误报清零。所以未来的迭代顺序应该是：

1. 用当前模型跑全视频，按置信度排出它拿不准的窗口（`training/_neg_candidates.py`）
2. 人工确认这些窗口（`training/label-train.bat`）
3. 写回（`training/label-apply.bat`）→ 重训 → 真值评估

详见 `training/LABELING.md`。

### 迭代过程中模型自己发现的新滑翔段

每一轮扫描都会找到人工标注漏掉的滑翔，全部经肉眼核对确认：

| 发现轮次 | 新增段 |
|---|---|
| v2 | p5 317.0、360.7；p3 345.7 |
| v3 | p3 58.67 |
| v4 | p3 14.6、44.4、48.4、60.4、238.8、275.6、282.0、297.8、445.6、448.0 |
| v5 | p3 46.3、64.7、98.3、283.0、348.7、454.0 |
| v6 | p3 115.0、239.0、244.0、264.3、364.0、426.0 |

**p3 实际有 22 段以上的滑翔，而最初人工只标了 4 段。**
这也是为什么帧级精确率在真值补全前看起来只有 0.39 —— 那是真值不全，不是模型不行。

## 3. 性能

实测机器：Ryzen 7 7735H (16 逻辑核, 4GB 可用内存) + RTX 4060 Laptop 8GB

### 3.1 推理

| 方式 | 单帧耗时 | 帧率 |
|---|---|---|
| 当前 OpenCV 小地图标记测量 | 1.03 ms | 967 fps |
| YOLOv8n ONNX CPU（4 线程） | 40.4 ms | 25 fps |
| YOLOv8n ONNX CUDA | 27.0 ms | 37 fps |
| YOLOv8n torch CUDA batch=8 | 2.9 ms | 345 fps |
| YOLOv8n torch CUDA batch=16 | 2.7 ms | 375 fps |

### 3.2 批量推理在 CPU 上是负优化

onnxruntime 1.31，CPU provider：

| batch | ms/帧 | fps |
|---|---|---|
| **1** | **24.6** | **41** |
| 4 | 30.3 | 33 |
| 8 | 33.3 | 30 |
| 16 | 36.0 | 28 |

批量只在 GPU 上有意义。工具的 `DetectBatch` 因此**逐帧调用**。

线程数（同一模型，CPU）：

| 线程 | ms/帧 |
|---|---|
| 1 | 96.1 |
| 2 | 55.3 |
| 4 | 37.3 |
| **8** | **29.2** |
| 16 | 78.6（超订，反而更慢） |

工具用 `ProcessorCount / 2`。

### 3.3 输入分辨率

模型导出为动态输入尺寸，可以按需降分辨率。实测（p5+p3 全量扫描）：

| 分辨率 | ms/帧 | 检出滑翔段 | 用时 |
|---|---|---|---|
| 320×320 | 9.6 | 17/27 | 410 s |
| 416×416 | 18.7 | 20/27 | 510 s |
| **480×480** | **23.6** | **20/27** | 530 s |
| 512×512 | 30.0 | 18/27 | 570 s |
| 640×640 | 50.0 | 20/27 | 679 s |

**480 是最佳平衡点**，也是工具的默认值（配置项 `glide_yolo_input_size`）。
640（训练分辨率）反而最慢，召回没有提升。

### 3.4 真正的瓶颈是视频解码

用 `VideoPathTool glide-profile` 拆分：

```
解码全部帧      :    71.3 s   (50228 帧, 1.4 ms/帧)
推理 1 帧      :     0.1 s   (56.5 ms/帧)   <- 只对采样帧做推理
```

解码每帧 1.4ms（全部 25114 帧），推理只对 1/10 的采样帧做。
480 分辨率下推理降到 48.3 ms/帧。

### 3.5 训练效率优化

最初训练只用 **6% 的 GPU** —— 瓶颈是每个 epoch 都要解码 1058 张 1920×1080 的 JPEG。

**优化一：预缩放数据集**。把图片按推理时的 letterbox 方式（等比缩放 + 居中 padding 114）
一次性缩到 640×640 存盘，解码量降到约 1/5。

**优化二：加大 batch**。

| 配置 | 秒/epoch | GPU 峰值 | GPU 平均 |
|---|---|---|---|
| 原始 1920 + batch 8 | 40.2 | 79% | 23% |
| 640 预缩放 + batch 8 | 38.3 | 82% | 35% |
| 640 预缩放 + batch 16 | 32.4 | 89% | 33% |
| **640 预缩放 + batch 32** | **29.6** | **93%** | 26% |
| 640 预缩放 + batch 8 + 4 workers | 36.3 | 80% | 28% |
| 640 预缩放 + batch 8 + 8 workers | 48.1 | 73% | 28% |

多 worker 在这台机器上**更慢**（Windows 进程启动开销 + 只有 4GB 可用内存）。

**最终配置**：预缩放 640 + batch 32 + 2 workers。
60 epoch 的实测耗时 **443~511 秒**（7.4~8.5 秒/epoch）。

### 3.6 各代训练耗时

| 代 | epochs | 耗时 | s/epoch |
|---|---|---|---|
| v3 | 40 | 1085 s | 27.1 |
| v4 | 40 | 955 s | 23.9 |
| v5 | 60 | 468 s | 7.8 |
| v6 | 60 | 511 s | 8.5 |
| v7 | 60 | 443 s | 7.4 |

**提速 3 倍**（v4 → v5 的差异来自预缩放 + batch 32）。

## 4. 半监督迭代流程

按建议实现，不做全量重扫：

```
1. 用当前模型 5fps 扫描全视频（阈值降到 0.10，把弱检也报出来）
2. 人工核对扫描结果里所有"窗口外"的检测
   —— 模型自己找到的滑翔段比人工标注的多得多
3. 把确认的段加进标注窗口（分 VERIFIED / NEW 两类）
4. 用模型在窗口内逐帧打分，只取分数最高的 N 帧做正样本
5. 从上一轮权重微调
6. 3fps 全视频评估，选出最优的一代
```

**第 2 步是整个流程的价值所在。** p3 实际有 22 段以上滑翔，
而最初人工只标了 4 段。每一轮迭代都会发现新的：

| 轮次 | 新发现 |
|---|---|
| v2 | 3 段 |
| v3 | 1 段 |
| v4 | 10 段 |
| v5 | 6 段 |
| v6 | 6 段 |

**第 4 步的关键细节：每窗取最置信的 N 帧，而不是整窗采样。**
滑翔持续几秒，中间有起跳和收翼的过渡帧（翼还没展开），
模型在那些帧上是沉默的。整窗采样会把这些帧标成正样本 —— 这正是
第 3 轮训练（precision 0.20）比第 2 轮（0.68）差的原因。

实测每窗的分数分布（v3 模型，p5 已验证窗口，226 帧）：
中位数 0.30，但有 6 个窗口的中位数是 **0.000** —— 模型完全没输出，
说明那些窗口里确实有大量非滑翔帧。

**第 5 步**：从零训练在 ~150 正样本上很不稳定；
从上一轮权重微调则稳定收敛。

**安全网**：写数据前检查每个负样本是否落在滑翔窗口 ±0.5s 内，命中就丢弃。
在 v7 这一轮拦下了 **29 个**这样的负样本 —— 早期版本正是因为
p3 275.0~281.7s 这个窗口里**含有一段真滑翔**（275.6~275.8），
才把训练数据搞脏的。

**迭代不是单调变好的**：v7 的召回更高（帧级 F1 0.752），
但引入了 5 个披风误报。最终采用 v6（误报 1 个，mAP50 0.870）。

## 5. 集成到工具

### 依赖
```xml
<PackageReference Include="Microsoft.ML.OnnxRuntime" Version="1.20.0" />
```
用 ONNX Runtime 而不是 Python side-car，工具保持单一可执行文件。

### 新增文件
| 文件 | 内容 |
|---|---|
| `Core/GlideYoloDetector.cs` | ONNX 推理封装（letterbox 预处理 + 可调分辨率） |
| `GlideDetectTest.cs` | 命令行自检：`VideoPathTool glide-test <model.onnx> <video> [fps] [conf]` |
| `GlideProfileTest.cs` | 性能剖析：`VideoPathTool glide-profile <model.onnx> <video> [fps]` |

### 关键实现细节

**预处理必须与 Ultralytics 一致（等比缩放 + 居中 padding，灰底 114）**。
用直接拉伸会改变翼的宽高比，检测数会**归零**。
已用 Python 逐帧对比验证：input diff = 0.0000，输出 diff = 0.000000。

**NCHW 批次布局**：批次偏移是 `i * 3 * plane`，不是 `i * plane`。
（这个 bug 曾导致批量推理只检出 12 帧而不是 95 帧。）

**不要在 CPU 上批量推理**（见 3.2）。

### 配置项
```
[51] 使用YOLO检测滑翔: True
[52] 滑翔模型路径: glider.onnx
[53] YOLO置信度阈值: 0.30
[54] YOLO采样率(FPS): 3
[55] YOLO批大小: 8
[56] YOLO输入分辨率: 480
[57] 滑翔窗口外扩(秒): 1.0
```

模型文件缺失时**自动回退**到小地图启发式，并给出提示。

### 两个视频的正确小地图参数

| 视频 | 圆心 | 半径 | 裁剪比例 |
|---|---|---|---|
| p3.mp4 | (280, 269) | 290 | 0.8 |
| p5.mp4 | (230, 220) | 203 | 0.8 |

用错参数会让匹配几乎完全失败（见 6.3）。录制后若匹配成功率低于 60%，
工具会给出警告。

### 端到端验证
C# 的 ONNX 推理结果与 Python 的 ultralytics **逐帧一致**：
同样检出 7 段 p5 滑翔，分数完全相同（0.965 / 0.949 / 0.373 / 0.766 / 0.528 / 0.863 / 0.334）。

## 6. 集成到录制工具：完整录制实测

### 6.1 录制结果

| 路线 | 路径点 | fly 点 | 滑翔段 | 断点 |
|---|---|---|---|---|
| p3 (812s) | 167 | 22 | 22 | 2 传送 + 2 丢失 |
| p5 (396s) | 86 | 7 | 8 | 1 传送 + 1 丢失 |

**几何完全未受影响**：p3 的新旧两版 **167 个点坐标逐一相同**，
只有 18 个点的 `move_mode` 从 run 变成 fly。传送点也完全一致。

**fly 点定位精确**：每个 fly 点与它对应的采样点距离都是 **0.00u**，
时间戳全部落在 YOLO 报出的滑翔窗口内。

```
p5  fly (9197.61, 2863.72) <- t=17.50   dist=0.00u   窗口 17.7-24.3
    fly (9214.12, 2887.97) <- t=22.50   dist=0.00u
    fly (9236.75, 2912.68) <- t=28.50   dist=0.00u   窗口 26.7-30.7
    fly (9381.81, 3141.28) <- t=88.50   dist=0.00u   窗口 85.3-89.7
    fly (9536.79, 3094.15) <- t=217.50  dist=0.00u   窗口 214.3-217.7
    fly (9891.81, 2868.17) <- t=318.00  dist=0.00u   窗口 317.0-317.7
```

### 6.2 滑翔窗口外扩

`glide_window_pad_sec`（默认 1.0 秒）把窗口两端各外扩 1 秒。
检测器只在翼完全展开时触发，但角色在那之前已经腾空、之后还在下落 ——
那段时间走不了路，属于滑翔段的一部分。

### 6.3 一个必须注意的坑：小地图参数按视频而异

**p3 是 (280, 269) 半径 290，p5 是 (230, 220) 半径 203。**
用错参数会导致 18.5s 之后**全部匹配失败**（confidence 归零），
中间整段变成一个 301u 的假"传送"，路径点从 86 个掉到 63 个。

已经加了两道防护：

1. **录制后检查匹配成功率**，低于 60% 时明确提示"请确认小地图圆心/半径"
   （选项 [2] 可自动检测当前视频的小地图圆）
2. 本报告记录两个视频的正确参数

### 6.4 集成后的行为

- 模型文件缺失 → 自动回退到小地图启发式，并打印提示
- `glide_use_yolo=false` → 强制用启发式
- 两种方式都失败 → 不标记任何 fly 点
- 滑翔检测**独立于**路径录制（录制时非采样帧只 Grab 不 Read，
  没有可用的图像），因此会额外解码一遍视频：
  p3 约 3 分钟，p5 约 5.3 分钟（320.8s）
- RebuildFromCsv（选项 [7]）也支持 YOLO：直接扫视频，不依赖 marker CSV

## 6. 回答你的三个问题

### Q1：准确率会高吗？

**会，但前提是标签必须干净，而且要用真值严格评估后再决定采用哪一代。**

最终 v6 在完整真值（29 段）上的表现：

| 方案 | 段级检出 | 误报 | 帧级 P | 帧级 R | 帧级 F1 |
|---|---|---|---|---|---|
| 小地图启发式 | 9/12 | **4 段** | 0.64 | 0.72 | 0.75 |
| **YOLO v6** | **26/29** | **1 段** | 0.851 | 0.539 | 0.660 |

三个必须说清楚的限制：

1. **真值本身不完整**。p3 实际有 22 段以上滑翔，最初人工只标了 4 段。
   模型每轮都在找出人工漏掉的段，这些段经核对确认后补进真值。
   真值补全前帧级精确率只有 0.39 —— 那是真值不全，不是模型不行。
2. **迭代不是单调变好的**。v7 召回更高（帧级 F1 0.752）但引入了 5 个披风误报，
   最终采用误报更少的 v6。**必须每次都严格评估**。
3. **样本量仍偏小**（164 正样本 / 2 个视频 / 2 个角色），
   换新角色或新地图很可能需要重训。

### Q2：需要多少训练集？

**实测下来，正样本 ~140 张（伪标签）就够训出可用模型**（v6 = 141 正 + 946 负）。

- 每段滑翔按 0.2 秒间隔打分，**每窗取最置信的 14 帧**
- 负样本几乎免费，但**必须刻意加入难负样本**（披风段 p5 108~121s 是最关键的一组）
- **难负样本的占比决定精确率**：v6 的精确率 0.836 主要靠这个

**扩大的建议**：
- 每个角色/配色 20~30 张（不同配色、不同视角、不同背景）
- 至少 3~5 个不同地图环境
- 难负样本（披风、其它展开类技能、传送道具）占比不低于正样本的 3 倍
- 目标：**300~500 正样本** 达到稳定可用；**1000+** 才算充分

**视频数量比帧数量更重要**：只有 2 个视频、2 个角色，
泛化能力完全没被验证过。加新视频（新角色、新配色、新地形）比加同一视频的更多帧有效得多。

### Q3：性能要求高吗？

**不高。**

- 训练：RTX 4060 上 60 epoch **7.4~8.5 秒/epoch**（约 8 分钟一轮）
- 推理：ONNX CPU **48 ms/帧**（480 分辨率），工具只要 3fps，**CPU 足够**
- 模型：12.3 MB，可直接随工具分发
- 真正的开销是**视频解码**（1.4 ms/帧 × 全部帧），不是推理

如果只需要 CPU，yolov8n 是合适的选择；yolov8s 更准但慢 3~4 倍
（实测 batch=16 时 yolov8s 反而比 yolov8n+batch=32 更慢）。

## 7. 仍需注意

1. **正样本量仍偏小**（141），且只来自 2 个视频 / 2 个角色，
   泛化能力完全未经验证。换新角色/新地图很可能需要重训。
2. **真值仍不完整**。已确认 29 段，但 p3 可能还有漏掉的。
   每次迭代都应重新扫一遍并人工核对窗口外的检测。
3. **自动框选有噪声**："宽且居中"比"取最大连通域"好很多
   （跳过的帧从 30 降到 6），但仍不是人工标注。
4. **C# 端目前只做了 CPU provider**，没有配置 GPU
   （ONNX Runtime 默认走 CPU，已够用；需要时加
   `SessionOptions.AppendExecutionProvider_CUDA()`）。
5. 训练脚本依赖独立 venv（`video/.venv-yolo`，numpy<2 + torch 2.3.1），
   因为全局环境的 torch 2.3.1 与 numpy 2.x 不兼容。
6. 训练/评估脚本在 Windows 上跑 ultralytics 的 `model.val()` 需要
   `if __name__ == '__main__':` 保护，否则会报
   "An attempt has been made to start a new process before the current process
   has finished its bootstrapping phase"。
7. **不要同时跑两个训练进程写同一个输出目录** —— 会互相覆盖 results.csv，
   出现过两次"epoch 数突然归零"的怪现象。训练和评估已拆成
   `_train.py` 和 `_eval.py` 两个独立脚本。
